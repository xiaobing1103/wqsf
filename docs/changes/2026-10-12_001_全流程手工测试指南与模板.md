## 3. 修改前后的逻辑

### 修改前

需要在各轮变更记录、后端 Review 和前端规范之间来回查找测试方式；没有统一的执行状态和缺陷记录格式。

### 修改后

```text
启动检查
  -> 两端登录
  -> 后台基础功能
  -> 小程序页面导航
  -> 客户报单与后台审核补件闭环
  -> 商标/资质/品类匹配
  -> 导入导出/审计/权限边界
  -> 微信模拟器/真机/生产分层验收
```

工作簿根据“全流程用例”的状态自动计算总览。失败用例通过缺陷编号关联“缺陷记录”。

## 7. Bug 定位和回退

- 启动失败先看 Docker 状态、`wqst-api-dev` 日志和手工测试指南第 7 节。
- 工作簿需要调整时继续使用 Artifact Tool，修改后必须再做公式扫描和四表渲染。
- 文档回退时删除本轮新增文件，并恢复四份索引/Review 文档的本轮条目。
- 测试管理员如需回退，应通过后台账号维护流程处理，不直接删除历史关联数据。

## 8. 已知限制

- 本轮只完成启动和认证/只读冒烟，没有代替用户执行 111 条会改变业务数据的手工用例。
- Docker Desktop 启动前出现失效运行时套接字。旧临时运行目录已隔离为带时间戳的 `*.broken.*` 目录；这些目录不包含项目数据库卷。
- Docker 日志记录到界面端一次“Reset to factory defaults”操作，但当前项目命名卷仍存在，三个容器和既有数据均可访问。本轮没有主动执行重置命令。
- 腾讯云 OCR、正式微信登录/绑定、微信客服、微信真机和生产环境依赖外部配置，不能写成已通过。
